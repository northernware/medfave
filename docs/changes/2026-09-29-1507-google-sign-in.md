# Continue with Google (web and API)

Opened: 2026-09-29 15:07 PHT · Updated: 2026-09-29 15:48 PHT

## What
- **"Continue with Google"** on `/login` and `/signup`, done by Medfave
  itself with `arctic` (PKCE, state in a short-lived signed cookie). No
  hosted auth service. Hidden until `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` are set.
- **Matching:** by the linked Google id first, then by Google-verified email.
  Never a second account for one email.
  - Linking to an account that **never confirmed its email** removes its
    password and ends its sessions (someone may have signed up with another
    person's address in advance). The owner can set a password with "Forgot
    password".
- **New people** land on `/signup/google`: patient or doctor, name, and the
  privacy consent. No account exists until they send it. Google accounts are
  created already verified, with no password.
- **The app:** `GET /auth/google?app=…&challenge=…` runs the same flow in a
  browser session and returns to the app with a two-minute one-time code;
  `POST /api/v1/auth/google/exchange { code, verifier }` trades it for a
  token. `GET /api/v1/auth/providers` says whether Google is on. Return
  links: `medfave://` only in production; `exp://` and localhost in dev.
  Documented in `docs/api.md`.
- Changing a password on an account that has none now says to use "Forgot
  password" instead of failing.
- Two "medfave." sentence endings the capitalisation sweep missed.

## Why
Phase 1b of plans/registration.md: one tap instead of a form, and email
arrives verified. Free.

## Tested
- `tsc` and `eslint` pass. Migration applied to the dev DB; `db:verify` passes.
- Against a test server with placeholder Google keys, in headless Chrome and curl:
  - start redirects to Google with PKCE, `prompt=select_account`, and the
    `APP_URL` callback; another host name is sent to `APP_URL` first;
  - a non-app return link or bad challenge is refused (400); callback without
    the state cookie → `failed`, cancelled → `cancelled`;
  - `/signup/google` (pending cookie minted in the test): new web doctor →
    doctor welcome, verified, no password, consent stored, identity linked;
    new app patient → redirect to the app with a code; wrong verifier 401,
    right one → token; linking to an unconfirmed account → still one account,
    password removed, old token and old password refused.
- **A real Google sign-in works** on localhost with the owner's OAuth client
  (testing mode). Not yet from a phone: that needs a public \`APP_URL\`.

## Heads-up
- **Migration** `20260929T0651_google_sign_in` (already applied to the shared
  dev DB): new `AccountIdentity` table, `Account.passwordHash` now nullable.
  Code reading `passwordHash` must allow null.
- **New env vars** `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (see
  `.env.example`). Google only accepts `localhost` or a public domain as a
  redirect, so **testing from a phone needs a public URL** (a deployment or a
  tunnel) as `APP_URL`; a LAN IP won't work.
- New dependency: `arctic`.
